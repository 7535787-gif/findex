# Lab 08 — результати профілювання та оптимізації

## M1. Профілювання до оптимізації

Вимірювання cProfile збережені у `docs/profiling/`. Індекс містить 11
документів і 967 436 термінів; пошуковий запит — `його вода роки`, 100 повторів.

### Три основні гарячі точки

| Гаряча точка | cProfile | Scalene | Гіпотеза до перевірки | Висновок після профілювання |
|---|---:|---|---|---|
| `build_partial()` під час `build_index()` | 75.016 с cumulative | Python-level orchestration; включає токенізацію | Основний час витрачається на Python-цикл побудови часткових індексів | Найбільша сукупна точка побудови; оптимізувати потрібно внутрішній pipeline, але не можна приписувати весь час тільки Python |
| `tokenize()` / `unicodedata.normalize()` | `tokenize`: 64.699 с cumulative; normalize: 59.267 с | `tokenize`: 0% Python, близько 8% native у профілі Scalene; `match.group()` також native | Нормалізація та вилучення токенів можуть бути дорожчими за саму логіку індексу | Значна частина витрат перебуває у вбудованих/native операціях Unicode та regex, а не в Python-операторах |
| `make_snippet()` / `re.Pattern.search()` | `make_snippet`: 33.287 с cumulative; regex search: 30.989 с | `make_snippet`: близько 0% Python і 12% native у пошуковому профілі; читання файлів також native | Формування snippets може домінувати над власне ранжуванням | Підтверджено: повторне читання документів і регулярні вирази є основною вартістю пошукового шляху |

**Примітка щодо інтерпретації:** cumulative time вкладених функцій не можна
додавати між собою — це призведе до подвійного рахунку. Значення cProfile і
Scalene отримані різними інструментами та під різним instrumentation overhead,
тому їх використовують для визначення гарячих точок і типу роботи, а не для
прямого порівняння абсолютних секунд.

## M2. NumPy ranking

NumPy-представлення зберігає `doc_ids`, `tfs` і довжини документів у
`int32`; ранжування BM25 і TF-IDF перевіряється порівнянням з базовою
реалізацією. Тести перевіряють ідентичний порядок документів та оцінки,
включно з довгими списками postings і tie-break.

Поточні вимірювання та пояснення наведені в [`numpy-benchmark.md`](numpy-benchmark.md).
На корпусі з 11 документів NumPy не завжди швидший: накладні витрати масивних
операцій переважають для коротких списків. На синтетичному індексі з 10 000
документів довгі списки postings дали 58.59× прискорення у збереженому запуску.

## CI

`pytest-benchmark` є dev-залежністю. `tests/test_benchmarks.py` вимірює
базові `search` і `build_index` на фікстурному корпусі. CI встановлює dev
dependencies та запускає повний pytest suite. Статус реального GitHub Actions
run треба перевіряти у GitHub; локальна наявність workflow не доводить, що
віддалений run успішний.

## M3. Semantic та hybrid

У репозиторії є `findex embed`, chunk embeddings, semantic search, RRF hybrid
search та параметр режиму в CLI/API/UI. `scripts/evaluate_semantic.py`
формує таблицю keyword / semantic / hybrid Precision@5 для 10 початкових
запитів і 5 перефразів. Фактичну таблицю з оцінками потрібно отримати запуском
скрипта з моделлю та embeddings для `index-lab04.bin`; ці значення не
генеруються без виконання моделі.
